# Which open agent standards (MCP, ACP, Agent Skills, and the Claude Code, Codex, and Cursor plugin formats) can carry DropTerm's plugin system and AI capability, in what roles, and at what cost?

**Question:** Which open agent standards — MCP (Model Context Protocol), ACP (Agent Client Protocol), the Agent Skills SKILL.md format, and the adjacent Claude Code / Codex / Cursor plugin formats — could carry DropTerm's plugin system and AI capability, in which roles (DropTerm as client/host, as server/agent-runner, as skill target), at what maturity, and at what cost in Rust on DropTerm's pinned build graph?

**Date:** 2026-11-26

**TL;DR:** MCP is the one standard that can carry a DropTerm-hosted AI capability today — as a client/host over the official Apache-2.0 `rmcp` SDK (stable spec 2026-07-28; nearly every hard dependency is already in `Cargo.lock`) it buys a Lua-free plugin tier where a plugin is a spawned MCP server whose tools become palette rows and whose resources become panel reads, and as a stdio MCP server it exposes the terminal to external agents at the cost of a new reply-capable IPC seam and a capability-grant ruling; ACP carries an agent running in the right rail (v1 stable, crate 5.6.1, powers Zed) and nothing else — it has no plugin surface and no completion surface (the prior record's rejection stands); Agent Skills carry no plugin runtime at all — a SKILL.md executes inside an AI agent, not inside DropTerm — so the plugin creator's AI path is a DropTerm *authoring skill* (instructions plus validation scripts any skills-capable agent can run), and the new vendor-neutral Agent Plugins 1.0 wrapper (Amazon/Cursor/Microsoft/OpenAI/Vercel TSC) is a distribution option for that skill, never a replacement for the Lua host.

## Findings

### 1. MCP's current stable revision is 2026-07-28, and the 2026 restructure changed the shapes an integrator builds against

- The specification page names the authoritative schema as `schema/2026-07-28/schema.ts` ([MCP specification](https://modelcontextprotocol.io/specification/latest), fetched 2026-11-26). The official Rust SDK states: "This SDK implements the stable MCP 2026-07-28 specification while remaining fully compatible with the 2025-11-25 release and earlier versions" ([modelcontextprotocol/rust-sdk README](https://github.com/modelcontextprotocol/rust-sdk), fetched 2026-11-26).
- Architecture: "The Model Context Protocol (MCP) follows a client-host-server architecture where each host can run multiple client instances"; "A host application creates and manages multiple clients, with each client having a 1:1 relationship with a particular server." A host "Controls client connection permissions and lifecycle … Enforces security policies and consent requirements … Handles user authorization decisions" ([architecture.md](https://modelcontextprotocol.io/specification/2026-07-28/architecture.md), fetched 2026-11-26).
- The 2026-07-28 revision made the protocol per-request stateless: "MCP is a stateless protocol: every request is self-contained and carries its own protocol version and capabilities." Capability negotiation moved into `_meta.io.modelcontextprotocol/clientCapabilities` on every request plus an opt-in `server/discover` up-front call. "Earlier protocol revisions established a connection-scoped session with an `initialize` handshake and allowed servers to initiate JSON-RPC requests. Clients and servers that interoperate with those revisions detect the counterpart's era and fall back" ([architecture.md](https://modelcontextprotocol.io/specification/2026-07-28/architecture.md), [transports.md](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports.md), both fetched 2026-11-26).
- Sampling and roots are deprecated at this revision: "Sampling and roots requests are also delivered via `InputRequiredResult`, but both are deprecated as of protocol version `2026-07-28` and should not be used in new implementations" ([architecture.md footnote](https://modelcontextprotocol.io/specification/2026-07-28/architecture.md); the roots page carries the same warning citing SEP-2577). Servers request user input through the multi-round-trip `InputRequiredResult` pattern ([client.md](https://modelcontextprotocol.io/specification/2026-07-28/client.md), fetched 2026-11-26). Any 2024/2025-era MCP write-up describes a protocol that no longer matches the stable revision; DropTerm integrations must read 2026-07-28.

### 2. The primitives: servers offer resources, prompts, tools; clients offer elicitation; security is consent-first

- "Servers offer any of the following features to clients: **Resources**: Context and data … **Prompts**: Templated messages … **Tools**: Functions for the AI model to execute. Clients may offer the following features to servers: **Elicitation**: Server requests for additional information from users." Utilities include "Progress tracking, Cancellation, Subscriptions, Completion, Pagination, Caching, Error reporting" ([MCP specification overview](https://modelcontextprotocol.io/specification/latest), fetched 2026-11-26).
- The spec's own security principles are load-bearing for DropTerm: "Tools represent arbitrary code execution and must be treated with appropriate caution. … descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server. Hosts must obtain explicit user consent before invoking any tool" ([MCP specification, Security and Trust & Safety](https://modelcontextprotocol.io/specification/latest), fetched 2026-11-26).
- Authorization is transport-scoped: "Authorization is **OPTIONAL** … Implementations using an HTTP-based transport **SHOULD** conform to this specification. Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment." The HTTP flow is OAuth 2.1 (draft-13) with PKCE, RFC 8707 resource indicators, and RFC 9728 protected-resource metadata ([authorization.md](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization.md), fetched 2026-11-26). For stdio — the transport DropTerm would use in both roles — the spec prescribes no auth surface at all; trust lives in the user's decision to run the server.

### 3. Two standard transports, both process-shaped: stdio and Streamable HTTP

- "1. [stdio]: newline-delimited messages over the standard streams of a client-launched subprocess. 2. [Streamable HTTP]: each message is an HTTP POST to a single MCP endpoint; replies arrive as a JSON object or a request-scoped SSE stream." Custom transports are allowed if they preserve JSON-RPC framing ([transports.md](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports.md), fetched 2026-11-26). Both roles DropTerm could play (client of spawned servers; server spawned by an agent) are stdio-shaped — the HTTP transport and its OAuth machinery sit with the provider-transport record, not here.

### 4. The official Rust SDK is `rmcp` 3.11.0 — Apache-2.0, tokio-based, and its hard dependencies are already in DropTerm's lock file

- crates.io: `rmcp` 3.11.0 (published 2026-11-17), license Apache-2.0, description "Rust SDK for Model Context Protocol", repository `https://github.com/modelcontextprotocol/rust-sdk/`, 55,164,050 total downloads, 74 versions, recent releases published by Alex Hancock under the `modelcontextprotocol` organization ([crates.io API](https://crates.io/api/v1/crates/rmcp), fetched 2026-11-26). The repo describes itself as "An official Rust Model Context Protocol SDK implementation with tokio async runtime" ([rust-sdk README](https://github.com/modelcontextprotocol/rust-sdk), fetched 2026-11-26).
- Non-optional dependencies: `futures ^0.3`, `serde ^1.0`, `serde_json ^1.0`, `thiserror ^2`, `tokio ^1`, `tokio-util ^0.7`, `tracing ^0.1`, `indexmap ^2` ([docs.rs/rmcp](https://docs.rs/rmcp/latest/rmcp/), fetched 2026-11-26). Cross-checked against `Cargo.lock` at HEAD: tokio 1.53.1 (line 7112), tokio-util 0.7.20 (7162), tracing 0.1.44 (7304), futures 0.3.34 (2059), serde_json 1.0.151 (6428), schemars 1.2.3 (6244, via gpui-pre), indexmap 2.14.2 (3484) — every hard dep is already in the graph. Optional deps (hyper ^1, hyper-util ^0.1, http-body-util ^0.1, rustls, tower-service) also resolve against versions already present via `gpui-pre-http-client` 0.3.12 (lock line 2595; hyper 1.12.0 at 3185, rustls 0.23.46 at 6128, tower 0.5.3 at 7277). New-to-the-graph are the rmcp crate pair itself and, if HTTP is ever enabled, `reqwest ^0.13.2` and the auth stack (`oauth2 ^5.0`, `jsonwebtoken ^11`).
- Feature flags: `server` (default), `client`, `macros`, `schemars` ("JSON Schema generation for tool definitions"), `auth`, `elicitation`, `skills-fs` ("Serve SEP-2640 skills from a directory tree (SkillCatalog)"), and transports `transport-io` ("Server-side stdio transport"), `transport-child-process` ("Client-side stdio transport (spawns a child process)"), `transport-async-rw`, `transport-streamable-http-client(-reqwest)`, `transport-streamable-http-server` ([docs.rs/rmcp](https://docs.rs/rmcp/latest/rmcp/), fetched 2026-11-26). Legacy HTTP+SSE server transport is a "deliberate non-goal for rmcp" ([rust-sdk README](https://github.com/modelcontextprotocol/rust-sdk), fetched 2026-11-26). The two features DropTerm's roles need — `client` + `transport-child-process` (DropTerm spawns servers), `server` + `transport-io` (agents spawn DropTerm) — are exactly the supported, documented path.
- Notable Rust adopters named by the SDK: goose (Block), apollo-mcp-server (Apollo GraphQL), containerd-mcp-server, nvim-mcp, rustfs-mcp, hyper-mcp, others ([rust-sdk README](https://github.com/modelcontextprotocol/rust-sdk), fetched 2026-11-26). Apache-2.0 is GPL-3.0-compatible (one-way, into GPL-3.0); DropTerm is GPL-3.0-only ([README.md](../../README.md), line 8) — no license obstacle in either role.

### 5. Skills over MCP (SEP-2640) is Final as a spec but has almost no host support yet

- "The Skills extension allows MCP servers to expose workflow instructions and supporting files to clients. … A skill is a directory containing a `SKILL.md` file and optional supporting files, following the Agent Skills specification. This extension defines discovery and retrieval over MCP." Servers declare `io.modelcontextprotocol/skills` and implement `skills/list` and `skills/get`; files are read through `resources/read` with a SHA-256 digest manifest the host must verify byte-for-byte before use, approval binding to the manifest, "Hosts MUST NOT retrieve files ahead of need", and a 512-files/16-MiB soft limit ([Skills extension overview](https://modelcontextprotocol.io/extensions/skills/overview.md), fetched 2026-11-26). SEP-2640 "is Final" (same page).
- Maturity caveat, from the extension's own client matrix: the only marked entries are ChatGPT "Partial", fast-agent "Partial", and MCP Inspector "Partial" — Claude Code, Claude Desktop, VS Code, Cursor, and Goose show no Skills-extension support ([client matrix](https://modelcontextprotocol.io/extensions/client-matrix.md), fetched 2026-11-26). The extension page itself concedes "SDK and host support is still being implemented." rmcp already has the server side (`skills-fs`), so a DropTerm MCP server could serve skills — but there is no evidence of host demand yet. Related extensions exist for Tasks (SEP-2663, in rmcp's `task_manager`) and MCP Apps (`io.modelcontextprotocol/ui`, interactive HTML in conversations — a chat-conversation concept with no DropTerm surface) ([client matrix](https://modelcontextprotocol.io/extensions/client-matrix.md), [rmcp docs.rs](https://docs.rs/rmcp/latest/rmcp/), both fetched 2026-11-26).

### 6. Terminal precedents: Warp and Zed are MCP *clients*; VS Code embeds MCP in Copilot; iTerm2's status is unverified; no surveyed terminal exposes itself as an MCP server

- Warp (client): servers configured as JSON (`command`/`args`/`env` for stdio, `url` for HTTP), trust rules "Project-scoped servers never auto-spawn" and "Config edits require approval" — recorded with sources in [terminal-plugin-systems](terminal-plugin-systems.md) (fetched 2026-11-21).
- Zed (client): "Zed currently supports MCP's Tools and Prompts features" and handles `notifications/tools/list_changed`; local servers via `command`/`args`/`env` JSON, remote via `url`/`headers` with the standard MCP OAuth prompt when no Authorization header is configured; MCP servers also installable as Zed extensions; per-tool permissions with rules keyed `mcp:<server>:<tool_name>` and a `confirm`/`allow`/`deny` default ([Zed MCP docs](https://zed.dev/docs/ai/mcp), fetched 2026-11-26). The page does not say which SDK Zed's client uses.
- VS Code (client, embedded in Copilot Chat): server types "HTTP (HTTP or Server-Sent Events)" or "Command (stdio)"; configuration lives in Copilot Global settings or a workspace-root `.mcp.json` for source-controlled sharing; the docs warn "Local MCP servers can run code on your machine, and tools can access services using your permissions" and direct users to "Review startup, sign-in, or tool approval requests as they appear" ([VS Code MCP docs](https://code.visualstudio.com/docs/copilot/chat/mcp-servers), fetched 2026-11-26).
- iTerm2: could not be verified — iterm2.com rate-limited every fetch attempt on 2026-11-26 (see Unverified).
- Role (b) precedent check: none of the surveyed terminals documents exposing the terminal itself as an MCP server. The observed pattern is third-party MCP servers built on a terminal's existing scripting surface (e.g. kitty's remote-control socket feeding community servers, per [terminal-plugin-systems](terminal-plugin-systems.md)). DropTerm-as-MCP-server would be a first among peers, which cuts both ways: differentiation, and no inherited security design.

### 7. ACP: v1 is the stable protocol, v2 is an explicit Preview — and v2 removed the client-side terminal APIs

- Versioning is a single integer negotiated at `initialize`; the client speaks first: "Clients **MUST** initialize the connection by calling the `initialize` method" with its latest supported version ([v2 initialization](https://agentclientprotocol.com/protocol/v2/initialization.md), fetched 2026-11-26). The v2 migration page states: "v2 as a whole is in Preview: it is ready to build on, and it is not frozen," and directs implementers to serve both: "Keep serving `protocolVersion: 1` peers when you add v2" ([v1→v2 migration](https://agentclientprotocol.com/protocol/v2/migration.md), fetched 2026-11-26). No release dates are published on the protocol pages.
- The v2 breaking-change list is the decisive fact for DropTerm: "The Client file system, terminal execution, and session modes APIs are gone" — explicitly including `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill`, `terminal/release` and the `fs/*` methods ([v2 migration](https://agentclientprotocol.com/protocol/v2/migration.md), fetched 2026-11-26). The client-terminal surface for v2 exists only as an RFD ([v2 client filesystem/terminal RFD](https://agentclientprotocol.com/rfds/v2/client-filesystem-terminal-capabilities.md), listed in the [docs index](https://agentclientprotocol.com/llms.txt), fetched 2026-11-26). In stable v1, these methods run on the client: "The Client runs these commands itself, so it is responsible for checking them," gated on `clientCapabilities.terminal`; `terminal/create` returns a `terminalId` immediately, `terminal/output` returns output with a truncation flag, and the security section tells clients to require `cwd` inside the session roots, apply policy to `command`/`args`/`env`, and display output "with terminal control sequences neutralized" ([v1 terminals](https://agentclientprotocol.com/protocol/v1/terminals.md), fetched 2026-11-26). A DropTerm ACP client must therefore pin protocolVersion 1 to keep the terminal seam.

### 8. What an ACP client (DropTerm as the editor) must implement

- Transport: "the editor boots the agent sub-process on demand, and all communication happens over stdin/stdout"; "ACP makes heavy use of JSON-RPC notifications to allow the agent to stream updates to the UI in real-time"; bidirectional requests cover "permission requests for a tool call"; the editor passes user-configured MCP servers to the agent, which connects to them itself ([architecture](https://agentclientprotocol.com/get-started/architecture.md), fetched 2026-11-26).
- Session surface (v2 baseline, the v1 equivalent minus resume/retry): "Supplying {} means the Agent supports the baseline session methods: session/new, session/list, session/resume, session/close, session/prompt, session/cancel, and session/update" ([v2 initialization](https://agentclientprotocol.com/protocol/v2/initialization.md), fetched 2026-11-26). The prompt turn is: client sends `session/prompt`, agent acknowledges acceptance, streams `session/update` notifications (message chunks, tool calls, plan), may issue permission requests and elicitation, client may cancel ([v2 overview](https://agentclientprotocol.com/protocol/v2/overview.md), fetched 2026-11-26).
- In DropTerm terms: one spawned CLI agent per session; `session/update` text rendered into a right-rail panel surface (the existing `panel_view` container); tool-permission requests rendered as the existing dialog slot's typed buttons; optionally `terminal/*` (v1) handed to a real DropTerm tab. Auth methods (`auth/login`/`auth/logout`) are optional and keyed off the agent's `authMethods` list ([v2 initialization](https://agentclientprotocol.com/protocol/v2/initialization.md), fetched 2026-11-26).

### 9. ACP adoption is broad and the Rust crate is maintained by the ACP organization

- The Rust crate `agent-client-protocol` is at 5.6.1 (updated 2026-11-25), Apache-2.0, repository `https://github.com/agentclientprotocol/rust-sdk`, 6,729,661 downloads, 95 versions ([crates.io API](https://crates.io/api/v1/crates/agent-client-protocol), fetched 2026-11-26); it "provides implementations of both sides of the Agent Client Protocol" via an `Agent` trait and a `Client` trait ([Rust library page](https://agentclientprotocol.com/libraries/rust.md), fetched 2026-11-26), and "powers the integration with external agents in the Zed editor" (same page). Note the repo lives under the `agentclientprotocol` org, not `zed-industries` — the protocol has its own governance home.
- Clients: Zed ("external agents support"), JetBrains ("through AI Assistant"), Neovim ("via CodeCompanion, agentic.nvim, avante.nvim, hermes.nvim"), Emacs ("via agent-shell.el"), VS Code (several extensions), Sublime Text, Qt Creator, Pulsar, Obsidian, Unity, plus a long tail of desktop/web/CLI/mobile clients ([clients directory](https://agentclientprotocol.com/get-started/clients.md), fetched 2026-11-26). The directory carries no official/community markers; listing is self-reported.
- Agents: Claude ("via Zed's SDK adapter"), Gemini CLI, "Codex CLI — via ACP's adapter (OpenAI)", OpenCode, Cursor ("Grok Build"), Qwen Code, Kimi CLI, GitHub Copilot ("in public preview", changelog dated 2026-01-28), Goose, Cline, Kiro CLI, OpenHands, Docker's cagent, and more ([agents directory](https://agentclientprotocol.com/get-started/agents.md), fetched 2026-11-26). This confirms — with sources — the adopter list that the 2026-11-23 completion record had from memory: Zed, JetBrains, Neovim, Emacs, and the Claude Code/Gemini CLI adapters all check out, and ACP still has "no shell-completion, ghost-text, or inline-suggestion surface" (finding 8 of [ai-completion-providers](ai-completion-providers.md) stands).

### 10. The Agent Skills spec: a folder with a SKILL.md, progressive disclosure, and a name/description contract — instructions for an agent, not code for a host

- Home and governance: "The Agent Skills format was originally developed by Anthropic, released as an open standard, and has been adopted by a growing number of agent products" ([agentskills.io](https://agentskills.io), fetched 2026-11-26). A reference validator ships at `github.com/agentskills/agentskills` (`skills-ref validate`) ([specification](https://agentskills.io/specification), fetched 2026-11-26).
- Format: "A skill is a directory containing, at minimum, a `SKILL.md` file" — YAML frontmatter plus Markdown body. Required frontmatter: `name` (max 64 chars, lowercase letters/digits/hyphens, must match the parent directory name) and `description` (max 1024 chars, "Describes what the skill does and when to use it"). Optional: `license`, `compatibility` (max 500 chars), `metadata` (string map), `allowed-tools` ("Experimental. Support for this field may vary between agent implementations") ([specification](https://agentskills.io/specification), fetched 2026-11-26).
- Progressive disclosure, the three levels: "**Metadata** (~100 tokens): The `name` and `description` fields are loaded at startup for all skills. 2. **Instructions** (< 5000 tokens recommended): The full `SKILL.md` body is loaded when the skill is activated. 3. **Resources** (as needed): Files … are loaded only when required," with `scripts/`, `references/`, `assets/` as recommended directories and "Keep your main `SKILL.md` under 500 lines" ([specification](https://agentskills.io/specification), fetched 2026-11-26).
- The decisive property for the plugin question: a skill's execution context is *an AI agent's* context. Nothing in the spec gives a skill a host-application API; `scripts/` are "executable code that agents can run" (same page) with "Supported languages … depend on the agent implementation." A SKILL.md cannot implement `dropterm.status_segment` or `panel_view` — those verbs exist only inside DropTerm's Lua host.

### 11. Who loads skills, and from where: Claude Code, Codex, Gemini CLI, opencode, Cursor — and `.agents/skills/` is emerging as the cross-tool path

- Claude Code: personal `~/.claude/skills/`, project `.claude/skills/`, enterprise managed settings, nested subdirectories, and plugin skills invoked "as `/plugin-name:skill-name`"; invocation control via `disable-model-invocation` / `user-invocable`; Claude Code extends the standard with many extra frontmatter fields (`when_to_use`, `argument-hint`, `model`, `context`, `agent`, `hooks`, `paths`, …) — outside Claude Code only the spec fields are accepted, and others "cause packaging/upload to fail" ([Claude Code skills docs](https://code.claude.com/docs/en/skills), fetched 2026-11-26).
- Codex: REPO `$CWD/.agents/skills` (plus parent and repo root), USER `$HOME/.agents/skills`, ADMIN `/etc/codex/skills`, SYSTEM bundled skills ("Includes skill-creator and skill-installer. Enabled by default"); implicit/model invocation plus explicit `/skills` or `$` mention; an extension manifest `agents/openai.yaml` carries `interface`, `policy` (`allow_implicit_invocation`), and `dependencies.tools` (MCP servers); the skill list budget is "at most 2% of the model's context window, or 8,000 characters" by default ([Codex build-skills docs](https://learn.chatgpt.com/docs/build-skills), fetched 2026-11-26 — developers.openai.com/codex/skills 308-redirects here).
- Gemini CLI: "Located in `~/.gemini/skills/` or the `~/.agents/skills/` alias" (user) and `.gemini/skills/` or `.agents/skills/` (workspace), with "the `.agents/skills/` alias takes precedence"; activation is model-driven through an `activate_skill` tool behind a consent prompt showing "the skill's name, purpose, and the directory path it will gain access to"; "Based on the Agent Skills open standard" ([Gemini CLI skills docs](https://geminicli.com/docs/cli/skills), fetched 2026-11-26).
- opencode: `~/.config/opencode/skills` and `.opencode/skills`, plus compatibility paths `~/.claude/skills`, `~/.agents/skills`, `.claude/skills`, `.agents/skills`; the model loads a skill "by calling the `skill` tool with its exact ID," users can invoke "as `@skill-id`" ([opencode skills docs](https://opencode.ai/docs/skills), fetched 2026-11-26).
- Cursor: skills are a plugin component (`skills/` subdirs with SKILL.md; a root-level SKILL.md alone is "single-skill plugin") ([Cursor plugins reference](https://cursor.com/docs/reference/plugins), fetched 2026-11-26).
- The convergence: Codex and Gemini CLI both treat `.agents/skills/` as a first-class (in Gemini's case, preferred) cross-tool location, and opencode reads it for compatibility. A skill written for DropTerm authoring would be discovered by all five surveyed loaders from `.agents/skills/` — which is also the path this repo already uses for its own pack.

### 12. The adjacent plugin formats: Claude Code, Codex, Cursor, and the new Agent Plugins 1.0 — all are agent-extension packages, and every one carries skills plus MCP servers as its portable core

- Claude Code plugins: "a directory of skills, agents, hooks, MCP servers, or other components that Claude Code installs and loads as one unit," manifest at `.claude-plugin/plugin.json` ("gives the plugin its name and can add a version, a description, and other metadata"); components include a JS "hooks module … which can also draw panes and add commands"; installed under `~/.claude/plugins/`; marketplaces are "a repository or directory with a `.claude-plugin/marketplace.json` … a catalog, not a hosted store"; the trust statement is plain: "a plugin you install can run code with your user privileges" ([Claude Code plugins docs](https://code.claude.com/docs/en/plugins), fetched 2026-11-26).
- Codex plugins: "Plugins distribute reusable skills and connectors through the universal plugin directory shared by ChatGPT and Codex. … can include one or more skills … optionally bundle registered MCP server connections … and presentation assets" ([Codex build-skills docs](https://learn.chatgpt.com/docs/build-skills), fetched 2026-11-26). The plugin-build reference page itself was not fetched (see Unverified).
- Cursor plugins, two formats: the "Agent Plugin (open standard)" with a root `plugin.json` ("Skills, MCP servers") and the "Cursor Plugin" with `.cursor-plugin/plugin.json` ("Skills, MCP servers, rules, agents, commands, hooks, variables"); manifest fields `name` (required, kebab-case), `description`, `version` (semver), `author`, `homepage`, `repository`, `license`, `keywords`, `logo`, plus component paths (`rules`, `agents`, `skills`, `commands`, `hooks`, `mcpServers`, `variables`); hook events include `sessionStart`, `preToolUse`, `afterFileEdit`, `beforeShellExecution`; a `.cursor-plugin/marketplace.json` lists plugins ([Cursor plugins reference](https://cursor.com/docs/reference/plugins), fetched 2026-11-26).
- Agent Plugins (agent-plugins.org): "Its version 1.0.0 specification defines a shared format for Agent Skills and MCP servers. Its initial Technical Steering Committee includes Core Maintainers from Amazon, Cursor, Microsoft, OpenAI, and Vercel." Layout: `plugin.json` + `skills/` ("Agent Skills in the format defined by the Agent Skills specification") + `mcp.json` ("stdio, Streamable HTTP, or legacy HTTP+SSE MCP servers") + "Reverse-domain extension namespaces let individual clients add behavior without changing the portable core"; and the scope line that matters: "distribution, installation, permissions, user experience, and client-specific capabilities remain under each client's control" ([agent-plugins.org](https://agent-plugins.org), fetched 2026-11-26).
- opencode plugins are the counter-shape — real host code, not agent instructions: `.opencode/plugins/*.ts|js` (global under the config dir), npm/git distribution via `opencode plugin add`, extending the agent itself with "tools, hooks, integrations, commands, agents" and, in Desktop, "panels, commands, or settings" via a `./gui-experimental` export ([opencode plugins docs](https://opencode.ai/docs/plugins), fetched 2026-11-26). These extend an *agent*, the same way Claude Code hooks extend Claude Code — no surveyed format lets a third party extend a terminal's UI.

### 13. Fit and cost on DropTerm's pinned build graph: the thread rule, the licenses, and the security posture

- Dependency cost is near-zero for the MCP client tier and small for ACP: both crates are Apache-2.0 and tokio-based, and DropTerm's lock already carries tokio 1.53.1, tokio-util 0.7.20, futures 0.3.34, schemars 1.2.3, serde_json, tracing, indexmap, and the hyper/rustls/tower stack (lines cited in finding 4). `agent-client-protocol` 5.6.1's own surface is "core protocol types and traits" (crates.io description) — no runtime framework. License compatibility: Apache-2.0 is one-way compatible with GPL-3.0; DropTerm is GPL-3.0-only, so both SDKs can be linked in either role.
- Thread model is the real constraint: rmcp and ACP are async-tokio machinery, and DropTerm's rule is that "no tokio channel crosses the bridge, so no foreign-thread waker can reach the foreground executor's pump" ([lua_host.rs](../../dropterm/src/core/lua_host.rs), lines 5-11) — the pty-test-gate class is exactly the failure mode to avoid ([pty-test-gate](pty-test-gate.md)). The architecture answer already exists in-tree: run the protocol client on the existing tokio runtime (the one serving D-Bus "beside the render loop" per [architecture.md](../architecture.md)) or a dedicated thread, and marshal into the UI over `std::sync::mpsc` like the Lua host does — protocol events become `HostCommand`-style enums the shell drains in its tick.
- Security posture: the standards push trust decisions to the host. MCP: "Hosts must obtain explicit user consent before invoking any tool"; tool descriptions are untrusted ([specification](https://modelcontextprotocol.io/specification/latest), fetched 2026-11-26). ACP: the client "is responsible for checking" terminal commands and should neutralize control sequences ([v1 terminals](https://agentclientprotocol.com/protocol/v1/terminals.md), fetched 2026-11-26). Peer discipline for the grants model: Zellij's 17-capability manifest and kitty's scoped socket passwords (recorded in [terminal-plugin-systems](terminal-plugin-systems.md)), plus Warp's "Project-scoped servers never auto-spawn" rule for checked-in config. DropTerm's own plugin trust model is stated plainly in the docs — full trust, "the way you treat a shell rc file" ([plugins.md](../plugins.md), lines 29-40) — and an MCP tier must not silently weaken that statement: spawned servers are arbitrary processes, so the consent surface (per-server grant, per-tool confirm like Zed's `mcp:<server>:<tool>`) is a product decision, not a protocol feature.

## What DropTerm has today

Grounded in local files at HEAD a83fb8f (2026-11-26):

- The plugin system is tiered Lua-first per the owner's 2026-11-21 ruling ([terminal-plugin-systems](terminal-plugin-systems.md)): a plugin is a directory `~/.config/io.github.l1br3_io.dropterm/plugins/<slug>/` holding `plugin.lua` plus an optional `plugin.json` manifest — "The manifest … declares what the host can say about the plugin without ever running its script": `name`, `commands[{id, description}]`, `settings[{key, type, label, default}]` over six types, `activation[]` (`on_startup`, `on_startup_finished`; each declared command implicitly derives `on_command:<id>`) ([plugins.md](../plugins.md), lines 44-121).
- The runtime: "one dedicated host thread owning one mlua interpreter for its life, speaking `std::sync::mpsc` both ways"; Lua 5.4, vendored mlua 0.12.2; "no tokio channel crosses the bridge, so no foreign-thread waker can reach the foreground executor's pump" ([lua_host.rs](../../dropterm/src/core/lua_host.rs), lines 3-11; Cargo.lock line 4178). Soft 100 ms / hard 1 s instruction-count bounds via a debug hook; a script blocked in a C call cannot be interrupted; "Editing anything in `plugins/` hot-reloads: the interpreter is recreated whole" ([plugins.md](../plugins.md), lines 371-395).
- The script API: `require('dropterm')` gives `on`/`emit` over seven terminal events; `status_segment`, `tab_title`, `command` with `send_text` as v1's one host verb; typed answers (styled spans); `dialog` (modal, typed buttons, `slot-event` replies); `panel_view` docking into the right rail, display + click only ([plugins.md](../plugins.md), lines 148-355).
- Trust model: "A plugin is your own config executing as you … There is no sandbox and none is claimed" ([plugins.md](../plugins.md), lines 29-36).
- UI seams an agent or protocol surface would reuse: the command palette (nucleo fuzzy search), the settings window's nine pages, the right panel rail, the dialog slot, script commands as keybind rows.
- Process seams: single-instance D-Bus where "Everything on this seam is fire-and-forget by design - it structurally cannot offer replies" ([architecture.md](../architecture.md), line 99); CLI verbs; plain-RON config store with a live watcher.
- Build graph (Cargo.lock at HEAD): tokio 1.53.1, tokio-util 0.7.20, futures 0.3.34, schemars 1.2.3, serde_json 1.0.151, thiserror 2.0.21, mlua 0.12.2, notify 8.2.0, zbus 5.19.0, nucleo-matcher 0.3.1, gpui-pre-http-client 0.3.12 with hyper 1.12.0 / rustls 0.23.46 / tower 0.5.3 — and **no MCP, ACP, or JSON-RPC crate anywhere in the graph**.
- Settled adjacent verdicts: completions stay builtin and ACP is rejected as the *completion* answer ([ai-completion-providers](ai-completion-providers.md)); WASM deferred, native dylibs never, Lua-first plugins ([terminal-plugin-systems](terminal-plugin-systems.md)); the declarative-schema record pins the script-vocabulary direction for richer plugin UI ([lua-declarative-ui-precedents](lua-declarative-ui-precedents.md)); invoked AI surfaces are [terminal-ai-surfaces](terminal-ai-surfaces.md), creator UX is [plugin-authoring-and-creator-ux](plugin-authoring-and-creator-ux.md), and HTTP transport, wire shapes, and secret storage are [ai-provider-transport-and-secrets](ai-provider-transport-and-secrets.md) — four records researched the same day, each owning one scope.

## Recommendation

**Proposed (three rulings for the owner): adopt MCP as the AI-facing protocol in both roles — client/host for a Lua-free plugin tier behind a spike, stdio server for terminal-to-agent exposure behind a grants ruling; adopt ACP v1 as the protocol if and when an in-rail agent surface is ruled in (the surface itself belongs to `terminal-ai-surfaces.md`); and build the plugin creator's AI path as a DropTerm authoring skill over the existing Lua format — no new plugin format.**

1. **Role (a), MCP client as the Lua-free plugin tier — spike first, adopt after.** A plugin = an MCP server process spawned under `transport-child-process`, whose `tools/list` entries merge into the palette/command registry exactly as manifest commands merge today (one seat per slug, manifest wins), and whose `resources/list` entries render as read-only right-rail rows through the typed-answers contract. This is the only standards-based way to get non-Lua plugins without WASM, and rmcp's feature set is built for it. The spike must prove the thread rule before any commitment: rmcp's client running on the existing tokio runtime (or its own), events marshaled to the UI over std-mpsc in the lua-host shape, with a foreign-thread-wake audit against the pty-test-gate gate. Until the spike passes, this stays Proposed.
2. **Role (b), DropTerm as a stdio MCP server — design the trust surface before the tools.** A `dropterm mcp-serve` child verb (rmcp `server` + `transport-io`) exposing exactly three tools — read the active tab's screen/scrollback, `send_text`, list tabs — is what external agents (Claude Code, Codex) can consume with zero host-side AI code. Two prerequisites, in order: a reply-capable IPC channel from the child to the live instance (the existing D-Bus seam is fire-and-forget by design and cannot serve tool calls; a new request/response zbus interface or a unix socket is a new seam the architecture doc must own), and an owner ruling on grants (per-tool confirm/allow/deny keyed like Zed's `mcp:<server>:<tool>`, kitty's scoped-password precedent for revocable subsets). Without the grants ruling this role does not start.
3. **ACP: protocol-ready, surface-gated.** Pin v1 (`protocolVersion: 1`) if an in-rail agent surface is ruled in: v2 is an explicit Preview that removed the client terminal APIs, so a DropTerm client keeping `terminal/*` must negotiate v1. The right-rail fit is real — `session/update` text paints through the panel container, `session/request_permission` maps onto the dialog slot's typed buttons — and the crate is both-sides, Apache-2.0, Zed-proven. What ACP does not do, twice confirmed: carry plugins (it has no extension surface) and carry completions ([ai-completion-providers](ai-completion-providers.md), finding 8).
4. **The plugin creator's AI path: an authoring skill, not a format.** Ship a DropTerm plugin-authoring skill — SKILL.md plus bundled validation scripts (`skills/` layout per the spec) that check a candidate plugin's `plugin.json` against the closed manifest vocabulary, the slug rules, and the Lua host's documented API. Any skills-capable agent (Claude Code, Codex, Gemini CLI, opencode, Cursor) discovers it from `.agents/skills/`, loads the instructions on demand, and writes a plugin into the plugins dir; DropTerm's existing hot-reload does the rest. Working precedents for skill-driven authoring ship in the wild: Codex bundles `skill-creator` and `skill-installer` as system skills, and this machine's own tooling ships a `plugin-creator` skill built the same way. Distribution can ride Agent Plugins 1.0 (`skills/` + optional `mcp.json` in one portable folder) once that spec's client list grows; the skill content is identical either way. The creator UX itself (in-app builder vs. skill, scaffolding flow) is owned by `plugin-authoring-and-creator-ux.md` — this record only rules that the AI vehicle is a skill over the existing format.
5. **Skills-over-MCP: watch, don't build.** SEP-2640 is Final and rmcp ships the server side (`skills-fs`), but the client matrix shows no full host support — only ChatGPT, fast-agent, and MCP Inspector partials. Revisit when a surveyed host ships it fully; until then it adds protocol surface for zero reachable users.

Rejected alternatives:

- **A skill (or Agent Plugin) as DropTerm's plugin format.** The spec's execution context is the agent's: scripts run "by agents," and nothing in the format reaches a host API. DropTerm's verbs (`status_segment`, `panel_view`, `dialog`, `command`) exist only in the Lua host. The plugin creator skill *writes* Lua plugins; it cannot *be* one.
- **Adopting Claude Code's or Cursor's plugin format as DropTerm's own.** Both manifest shapes (`plugin.json` + skills/agents/hooks/MCP components) package *agent* extensions — hooks fire in an agent session, agents are subagent definitions, panes drawn by a Claude Code "mod" are Claude Code panes. Their components have no DropTerm host to bind to, and the formats are versioned for their owners' runtimes, not ours.
- **ACP as the plugin system or the completion answer.** No plugin or completion surface (findings 7-8; the completion rejection was already ruled in [ai-completion-providers](ai-completion-providers.md)).
- **A first-party DropTerm plugin marketplace.** Every surveyed distribution point (Claude Code's, Cursor's) is explicitly "a catalog, not a hosted store" riding git; DropTerm's git-first theming path already covers data files, and a store is a maintenance liability with no peer-terminal precedent ([terminal-plugin-systems](terminal-plugin-systems.md), distribution findings).
- **Exposing richer MCP tools at v1 (spawn tabs, kill tabs, write to arbitrary tabs).** The spec's own framing — "Tools represent arbitrary code execution" — plus the kitty/Warp trust precedents say start read-mostly: screen read, send text (the v1 one-verb discipline DropTerm already chose for Lua), list tabs. Growth follows demand and the grants model, not protocol capability.
- **Skills-over-MCP server support at v1.** Zero full host support (finding 5); the directory-tree reader would serve skills nobody can consume.

### Feasibility

Work items, coarse-grained (units are modules/seams/files; no wall-clock figures):

- **MCP client tier (role a), after the spike passes:** one new module `dropterm/src/core/mcp/` (client manager: server spawn, capability negotiation, tool/resource caches — tokio-side, modeled on the generators runner's spawn/deadline/stale-while-revalidate shape already in `engine.rs`); one bridge enum + drain arm in the shell tick (the lua-host `HostCommand` pattern); palette/command registry merge rows (~1 file each); a Plugins-page extension or a new settings page for server rows and grants; docs (plugins.md section + configuration.md keys, which the docs gate pins). Roughly 5-7 items. New Cargo deps: `rmcp` (features `client`, `transport-child-process`, `schemars`, `macros`), no reqwest.
- **The spike (before any role-a commitment):** a bench that spawns a trivial MCP server child via rmcp on the existing runtime, drives a tool call, and runs the gpui test suite with the bridge armed — pass criterion is zero foreign-thread-wake aborts in the pty-test-gate class plus the two ignored tests staying green. One item; its failure is a hard blocker for role a as designed and would force either a dedicated protocol thread with pure-std marshaling or a re-think.
- **MCP server role (role b):** the `dropterm mcp-serve` CLI verb; the reply-capable IPC seam (a new request/response zbus interface beside the fire-and-forget V1 one, or a unix socket — an architecture-doc change either way); the three tools reading the engine's grid and spawn funnel; the grants UI on the settings window. Roughly 4-6 items, gated on the owner's grants ruling (hard blocker until then).
- **ACP right-rail client (if the surface is ruled in):** client harness over `agent-client-protocol` (v1 pin), a rail session view painting `session/update` through the panel containers, permission requests routed to the dialog slot, optional v1 `terminal/*` mapping to a real tab. Roughly 5-6 items. No hard blocker; depends only on the surface ruling owned elsewhere.
- **Plugin-authoring skill:** one SKILL.md, one validation script (manifest vocabulary, slug rules, API vocabulary checks), one docs page and a README index row. Roughly 3 items; no new dependencies; no blocker. This is the only piece that can ship immediately.
- **Versioning posture, all roles:** protocol revisions are pinned per release (MCP 2026-07-28, ACP v1) and negotiated at handshake — rmcp's `select_protocol_version` and ACP's `initialize` carry this; capability grants are DropTerm-owned config keys, additive per the house rule.

Hard blockers: none that are technical for the skill path or role a post-spike; the grants ruling (role b) and the in-rail surface ruling (ACP) are owner decisions; the thread-rule spike is a technical gate for role a.
