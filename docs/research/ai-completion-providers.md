# How do AI terminals architect shell completions and user-chosen models, and what should DropTerm's AI suggestion design copy?

**Question:** How do AI-enabled terminals architect shell autocompletions/suggestions — Warp (AI autosuggest, model picker, BYOK, privacy/consent, inline latency), Wave Terminal, Amazon Q CLI, GitHub Copilot CLI, Zed's language-model provider abstraction, and the Agent Client Protocol — so DropTerm can add an extendable, open `Ai` suggestion source with a settings surface where the user picks which AI model powers completions?

**Date:** 2026-11-23

**TL;DR:** No surveyed peer runs an LLM on the inline ghost-text keystroke path — Warp's own docs describe autosuggestions as "shell history and possible completions" with no AI, Amazon Q/Kiro shipped AI ghost text and then removed it entirely (Kiro CLI 3.0.0), Wave and `gh copilot` have no inline AI completion at all — so DropTerm should add `SuggestionSource::Ai` as one more additive variant that reads only engine-cached candidates (the generators runner's spawn/deadline/stale-while-revalidate pattern, already proven in `engine.rs`), behind an engine-side AI provider trait configured with one Zed-shaped `{provider, model}` selection key over a v1 single OpenAI-compatible custom provider (URL swap, the shape every peer converged on), API keys kept out of the config file (keychain/env per Zed and Wave), the source defaulted off as its own consent gate, and ranked below every local provider so stale or foreign truth never outranks local certainty.

## Findings

### 1. Warp's current autosuggest is history-based — its docs carry no AI ghost text at all

- Warp's autosuggestions doc describes a non-AI feature: Warp "will automatically suggest commands as you type based on shell history and possible completions," accepted with `→`/`Ctrl+F`, partially with `Ctrl+→` ([Autosuggestions docs](https://docs.warp.dev/terminal/command-completions/autosuggestions/), fetched 2026-11-23). The completions half is static: completions "will suggest commands, option names, and path parameters for you" ([Command completions overview](https://docs.warp.dev/terminal/command-completions/), fetched 2026-11-23).
- The agents section of the Warp docs index ([`_llms-txt/agents.txt`](https://docs.warp.dev/_llms-txt/agents.txt), fetched 2026-11-23) lists no AI-autosuggest, AI-completion, or ghost-text page anywhere; AI effort lives entirely under Agents (Agent Mode, CLI agents, inference). The one surface where Warp puts model intelligence near typing is Agent Mode's prompt input, not the shell line.
- Consequence for the survey question: the flagship "AI terminal" does not document an LLM behind its inline suggestions. Its completions architecture is exactly DropTerm's existing one — scraped history plus a static spec table — and its AI is a separate, explicitly invoked surface with its own inference settings.

### 2. Warp's model picker: an Auto family plus five provider families, user selection persists per session input

- Warp exposes Auto models (`auto`, `auto-efficient`, `auto-genius`, `auto-open` — "Auto models perform well across all agent workflows and are ideal if you prefer Warp to manage model selection dynamically"), OpenAI (GPT-6/5.x families with `low`…`max` reasoning suffixes), Anthropic (Claude Opus/Sonnet/Haiku/Fable with effort and `thinking` suffixes), Google (Gemini 3.x/4), xAI (Grok 4.x), and open-weights "Hosted via Fireworks AI" (GLM 5.3, Kimi K3, Minimax 3, Qwen 3.8 Max, DeepSeek V4.1 Flash) ([Model choice docs](https://docs.warp.dev/agents/inference/model-choice/), fetched 2026-11-23).
- The picker is a per-user UI affordance, not a per-feature matrix: "You can use the model picker in your prompt input to quickly switch between models … Your selection will automatically persist for future prompts." The dropdown carries "Intelligence, Speed, and Cost benchmarks," and a documented fallback exists — "The fallback model is selected to provide comparable quality and capabilities to your original choice" (same page).
- Retention disclosure rides the same page: models requiring provider retention (Anthropic's Claude Fable family) are listed inline, with "Turning off the **Help improve Warp** toggle doesn't remove these retention requirements" — model choice and data-handling facts are surfaced in the same picker ([Model choice docs](https://docs.warp.dev/agents/inference/model-choice/), fetched 2026-11-23).

### 3. Warp's BYOK and privacy/consent flow: custom OpenAI-compatible endpoints, keys in device secure storage, prompts pass through Warp's servers

- BYOK covers OpenAI, Anthropic, and Google keys, plus SuperGrok/ChatGPT subscriptions, and — the extendability answer — a "Personal custom inference endpoint" for OpenAI-compatible targets "like OpenRouter, LiteLLM, z.ai, or an internal gateway," available on the Free plan ([BYOK docs](https://docs.warp.dev/agents/inference/bring-your-own-api-key), fetched 2026-11-23).
- Key storage: "Personal API keys are stored in your device's secure storage." and "Warp does not retain your personal API key." (same page).
- The data path is explicit even for BYOK: "your prompt, context, and key pass through Warp's servers to that provider" and "BYOK prompts and responses pass through Warp's servers"; provider-side retention "depends on your provider account settings" (same page).
- Consent/opt-out: "You can disable Warp's AI features entirely in Settings > Agents > Warp Agent" ([Agents overview](https://docs.warp.dev/agents/), fetched 2026-11-23); "All users may opt out of telemetry at anytime and still continue using all of Warp, including our AI features" and enterprise ZDR — "Under provider Zero Data Retention (ZDR), AI providers must not retain your prompts and responses" ([Privacy docs](https://docs.warp.dev/support-and-community/privacy-and-security/privacy/), fetched 2026-11-23). Agent requests are the unit of exposure: "Agent requests send prompts and context to the configured model provider" ([Agent FAQs](https://docs.warp.dev/agents/getting-started/faqs/), fetched 2026-11-23).
- Inline ghost-text latency: no current Warp doc describes AI-powered inline suggestions or their latency handling — the documented latency machinery (fallback model, Auto routing) belongs to Agent Mode, not typing. See Unverified.

### 4. Wave Terminal: AI is a chat pane, not a completion source — config is named modes over provider presets plus a full-URL custom endpoint

- Wave's AI integrates as an AI widget/pane (chat with tools), not inline shell ghost text; its docs describe no completion integration ([Wave AI modes docs](https://docs.waveterm.dev/waveai-modes), fetched 2026-11-23).
- Settings schema (current): modes live in `~/.config/waveterm/waveai.json`, one entry per named mode with keys `ai:provider` (preset enum: `openai`, `openrouter`, `nanogpt`, `groq`, `google`, `azure`, `azure-legacy`, `custom`), `ai:apitype` (`openai-chat`, `openai-responses`, `google-gemini`), `ai:model`, `ai:endpoint` (full URL), `ai:apitoken`, `ai:apitokensecretname`, `ai:capabilities` (`tools`/`images`/`pdfs`); global selection via `settings.json` key `waveai:defaultmode` (set with `wsh setconfig waveai:defaultmode="ollama-llama"`), per-use switching via the mode dropdown ordered by `display:order` (same page).
- Local models ride the OpenAI-compatible path, not a named provider: Ollama/LM Studio/vLLM via `openai-chat` endpoints (e.g. `"ai:endpoint": "http://localhost:11434/v1/chat/completions"`; Ollama's `ai:apitoken` is "required but ignored") (same page).
- Keys are kept out of the config file: "API keys should be stored in Wave's encrypted secret store (`wsh secret set OPENAI_KEY=...`) rather than in config"; providers auto-derive secret names (`OPENAI_KEY`, `OPENROUTER_KEY`, …) (same page).
- The deprecated presets format ([AI Presets docs](https://docs.waveterm.dev/ai-presets), fetched 2026-11-23) carried a different provider list — `anthropic`, `perplexity`, `google`, `openrouter`, Azure, Ollama — under `presets/ai.json` with `ai:apitype`/`ai:model`/`ai:baseurl`/`ai:proxyurl`. The two pages disagree on the provider roster; both recorded, flagged under Unverified.

### 5. Amazon Q CLI → Kiro CLI: the one peer that shipped AI ghost text removed it entirely

- Amazon Q Developer CLI's public repo is in maintenance-only mode — the README states the project is "no longer being actively maintained and will only receive critical security fixes," superseded by the closed-source Kiro CLI; its `docs/` folder covers the agent chat only (no autocomplete docs) ([aws/amazon-q-developer-cli README](https://github.com/aws/amazon-q-developer-cli) and [docs/ listing](https://github.com/aws/amazon-q-developer-cli/tree/main/docs), fetched 2026-11-23; repo pinned at `15cc8f3cd18c`, last commit 2026-04-23).
- AWS's own docs page now redirects: "The Q CLI has become the Kiro CLI" ([AWS Q CLI docs](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/command-line.html), fetched 2026-11-23).
- Kiro CLI historically shipped two AI-powered shell features — an autocomplete dropdown and inline suggestions ("Gray 'ghost text' that appears as you type," accepted with Right/Tab) — both "automatically enabled after you install," governed by `kiro-cli settings autocomplete.disable true|false` and `kiro-cli inline enable|disable|set-customization [ARN]` (a Bedrock customization ARN, the model-selection seat) ([Autocomplete docs](https://kiro.dev/docs/cli/autocomplete/), fetched 2026-11-23).
- They are gone: "We have ended support for autocomplete and inline suggestions in Kiro CLI, and they have been removed from Kiro CLI 3.0.0," with users pointed to third-party tools "not developed, maintained, or supported by us" (same page). The one AI terminal vendor to put an LLM (via a Bedrock customization) on the ghost path has withdrawn the feature — the strongest single data point against AI-on-the-keystroke-path.
- Model choice for chat lives in the settings file `~/.kiro/settings/cli.json` as `chat.defaultModel` (e.g. `"claude-sonnet-4.6"`), alongside `telemetry.enabled` — model selection is a named-string key, global to chat, with no per-feature split documented ([Settings reference](https://kiro.dev/docs/reference/settings/), fetched 2026-11-23). No explicit AI consent flow is documented; the features were on by default and telemetry is a separate key (flagged under Unverified).

### 6. GitHub Copilot CLI: `gh copilot` has no model story; the successor CLI makes model choice a first-class `/model` + custom-provider surface

- The classic `gh copilot suggest`/`gh copilot explain` extension is deprecated — "GitHub Copilot in the CLI has been deprecated on October 25, 2025" — in favor of the standalone agentic Copilot CLI ([github/gh-copilot README](https://github.com/github/gh-copilot), fetched 2026-11-23; repo pinned at `98ba986c2ca3`, last commit 2025-10-30). Its only documented config is `gh copilot config` with "Optional Usage Analytics" and the "Default value for confirming command execution" — no model or provider key appears anywhere in the README; it is "powered by AI" via the Copilot platform with no documented user selection.
- The successor CLI makes model choice a first-class surface: `/model` in-session ("Use Shift+Tab to arrange the list into different model groupings: recommended, by vendor, by provider, or by category"), `copilot --model MODEL-NAME` on the command line, persistent default via `/config model`, and an auto-selection tier ("Copilot Fusion … chooses models, and execution patterns when needed, for your task") ([Choosing a model](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/choose-a-model), fetched 2026-11-23).
- Custom models are BYOK-style named providers in `providers.json` under `~/.copilot`: `"providers": [{ "name": "my-provider", "type": "openai", "baseUrl": "…", "apiKey": "…" }]` plus `"models": [{ "id": …, "provider": …, "wireModel": …, "maxPromptTokens": … }]`, with `type` of `openai` (covering "Ollama, vLLM, Foundry Local"), `azure`, or `anthropic`, optional `wireApi: "responses"`, and Ollama auto-discovery on `http://127.0.0.1:11434` (overridable via `OLLAMA_HOST`). Requirements: "Choose a model and endpoint that support **tool calling** … and **streaming**." The credential caution is explicit: "Credentials entered in this file are stored as plain text" ([Adding LLM models](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-llm-models), fetched 2026-11-23).

### 7. Zed: the nearest sibling's provider abstraction — named provider modules plus two user-keyed "compatible" maps, per-feature model selection, keys in the keychain

- The registry (`crates/language_models/src/provider.rs` at `zed-industries/zed@f126950f9d3b`, fetched 2026-11-23) ships named provider modules: `anthropic`, `anthropic_compatible`, `api_compatible`, `bedrock`, `cloud` (Zed-hosted), `copilot_chat`, `deepseek`, `google`, `llama_cpp`, `lmstudio`, `mistral`, `ollama`, `open_ai`, `open_ai_compatible`, `open_router`, `openai_subscribed`, `opencode`, `vercel_ai_gateway`, `x_ai`, `x_ai_subscribed` — with a shared `COMMON_RESERVED_HEADER_NAMES` guard ("Authorization", "Content-Type", "Accept") validating "the user-supplied custom-headers map once at settings load time."
- The settings struct (`crates/language_models/src/settings.rs`, same commit) carries one settings struct per provider — `anthropic`, `anthropic_compatible: HashMap<Arc<str>, AnthropicCompatibleSettings>`, `openai_compatible: HashMap<Arc<str>, OpenAiCompatibleSettings>`, `ollama`, `lmstudio`, `llama_cpp`, `open_router`, `bedrock`, `google`, … — and `api_url` exists on every provider except Zed's own; the `*_compatible` entries are **user-named** providers (map keys), each with its own `available_models` list.
- The compatible shapes are documented: `language_models.openai_compatible."my-provider".api_url` + `available_models: [{ name, display_name, max_tokens, … }]`, and the Anthropic twin with `custom_headers` and per-model `capabilities` ([Use API Access docs](https://zed.dev/docs/ai/use-api-access.md), fetched 2026-11-23).
- Key storage is a stated invariant: "Keys saved through Zed are stored in the system keychain, not in `settings.json`." and "Do not put API keys in `settings.json`"; env vars override — generated from the provider id "as upper snake case plus `_API_KEY`" (provider `my-gateway` → `MY_GATEWAY_API_KEY`) ([Use API Access docs](https://zed.dev/docs/ai/use-api-access.md), fetched 2026-11-23).
- Local servers are first-class named providers with the same keys: `ollama.api_url` (default `http://localhost:11434`), `auto_discover` (defaults true — the provider fetches and probes models itself, filtering `-embed` names and marking capability failures as disabled), `available_models`, `context_window`; keys optional via `OLLAMA_API_KEY`/`LLAMACPP_API_KEY`/`LMSTUDIO_API_KEY`, and `is_authenticated` is just reachability — "Always try to fetch models - if no API key is needed (local Ollama), it will work" ([Ollama provider source](https://github.com/zed-industries/zed/blob/main/crates/language_models/src/provider/ollama.rs) at `f126950f9d3b`; [Use a Local Model docs](https://zed.dev/docs/ai/use-a-local-model.md), fetched 2026-11-23).
- Model selection is per-feature over a common `{provider, model}` pair: `agent.default_model`, plus dedicated feature keys `agent.inline_assistant_model`, `agent.commit_message_model`, `agent.thread_summary_model`, `agent.compaction_model`, `agent.subagent_model`, `agent.inline_alternatives`, `agent.favorite_models` — each a `LanguageModelSelection { provider, model, enable_thinking, effort, speed }` ([agent_settings.rs](https://github.com/zed-industries/zed/blob/main/crates/agent_settings/src/agent_settings.rs) at `f126950f9d3b`; [Agent Settings docs](https://zed.dev/docs/ai/agent-settings.md), fetched 2026-11-23, e.g. `"default_model": { "provider": "anthropic", "model": "claude-opus-4-6" }`).
- Feature-provider decoupling is drawn explicitly: "Model access paths do not configure External Agents or Terminal Threads. External Agents and Terminal Threads usually own their own model access, auth, and configuration," and Edit Prediction "has its own provider setup under `edit_predictions`" ([LLM providers docs](https://zed.dev/docs/ai/llm-providers), fetched 2026-11-23) — i.e. even Zed does not give every feature one global model; each feature owns its selection key, and non-core features own their whole access path.

### 8. The Agent Client Protocol is a chat/session protocol, not a completion protocol

- ACP standardizes "a standardized protocol for agent-editor communication" (the LSP analogy: "Each editor must build custom integrations for every agent they want to support"), local transport "JSON-RPC over stdio," remote "over HTTP or WebSocket," reusing "MCP's JSON representations where possible" with custom types for "useful agentic coding UX elements, like displaying diffs" ([ACP overview](https://agentclientprotocol.com), fetched 2026-11-23; repo pinned at `zed-industries/agent-client-protocol@01a54c84f39`, 2026-11-22).
- Its scope is editor↔agent task assistance — sessions, prompts, permissions, diffs, Markdown streams. It has no shell-completion, ghost-text, or inline-suggestion surface. It is the protocol-level answer for *embedding agents*, not for sourcing completions; adopting it would buy DropTerm an agent-hosting capability, not an extendable completion provider seam.

### 9. Synthesis: the settings/extensibility surface every open peer converged on

- **Model choice is a `{provider, model}` pair, global default plus per-feature overrides.** Zed: `default_model` + one key per feature. Copilot CLI: `/config model` default + `--model`/`/model` per invocation. Warp: one persisted picker per input. Kiro: `chat.defaultModel` named string. Nobody ships a single global "the AI model" key that all features inherit.
- **OpenAI-compatible URL swap is the universal extension point.** Warp ("Personal custom inference endpoint … OpenRouter, LiteLLM, z.ai, or an internal gateway"), Wave (`custom` provider + full-URL `ai:endpoint`), Copilot CLI (`providers.json` `type: "openai"` + `baseUrl`), Zed (`openai_compatible`/`anthropic_compatible` user-keyed maps). Four of four implement generic-URL before or instead of per-vendor proliferation; Zed carries ~20 named providers *and still* ships the compatible maps because named adapters never exhaust the long tail.
- **Local servers ride the same shape with auto-discovery.** Zed's Ollama `auto_discover` + capability probing; Copilot CLI's Ollama discovery on `127.0.0.1:11434`; Wave's Ollama-as-OpenAI-endpoint. The pattern: point at the URL, list/fetch models, probe capabilities, surface in the same picker.
- **Keys never live in the settings file.** Zed: system keychain + `<PROVIDER>_API_KEY` env override, explicitly "not in `settings.json`". Wave: encrypted secret store with derived secret names. Warp: "your device's secure storage". Copilot CLI is the cautionary counter-example that documents its own flaw: "Credentials entered in this file are stored as plain text".
- **Consent is a feature-scoped off-switch plus invocation-scoped exposure.** Warp: disable-AI toggle, retention facts shown in the picker, "Agent requests send prompts and context to the configured model provider" (per-request framing). Kiro/Q: feature was always-on and is now deleted. The direction of travel is explicit, per-surface toggles, not one telemetry-style blanket.
- **No peer documents inline-LLM ghost text as a shipped, supported feature** — Warp's is gone from the docs, Q/Kiro's is removed, and the rest never had it. The AI-completion question every product actually answered is "which model backs my *invoked* AI surface," not "which model types my suffixes."

## What DropTerm has today

Verified against `dropterm/src/core/terminal/suggest.rs` and `dropterm/src/core/terminal/engine.rs` at HEAD (2026-11-23):

- The autosuggest model is pure and synchronous over one `Observation` snapshot; "the engine (Task 2) builds the observation under the term lock `update()` already holds and owns the `Suggest` state" (suggest.rs:8-11).
- The provider seam already anticipates AI: `SuggestionSource` (History, Path, Specs, Catalog, Generator) is the enum "the pipeline — eligibility, rendering, acceptance — talks to … so `Ai` and external providers join additively behind the same match later" (suggest.rs:36-47).
- "Every spawn, timeout, and cache population stays engine-side, outside the model, so the model itself still spawns nothing and never clocks" (suggest.rs:44-47). The generator runner is the proof: "spawn, deadline, and stale-while-revalidate cache engine-side" (engine.rs:641-642, runner at engine.rs:1103-1205), serving the model through `Observation.generator_candidates` (suggest.rs:102-118; populated at engine.rs:2614).
- The failure-stays-silent contract: "a suggestion shows only when every guard is certain, so any uncertain snapshot degrades to `None`, never to a wrong suffix" (suggest.rs:13-15), enforced by the guard chain (suggest.rs:449-492).
- The merge is a pinned, pure ranking — history first, then Path, Specs, Catalog, Generator (suggest.rs:503-511), `merged_candidate` taking the first non-`None` candidate (suggest.rs:1441-1457); a cached provider yields to fresh local truth ("a cached name may be stale, so nothing fresh ever defers to it", suggest.rs:494-502).
- An idle-delay display gate already exists (`autosuggestions_delay_ms`, Outcome::Withheld; suggest.rs:230-244, 479-481) and the engine resolves every `autosuggestions_*` config key into `TerminalOptions` (engine.rs:86-181) — both the debounce and the config seat an `autosuggestions_ai_*` key needs are in place.

## Recommendation

**Proposed: an engine-side `AiSuggestionProvider` trait + an additive `SuggestionSource::Ai` that reads only engine-cached candidates; model choice as one Zed-shaped `{provider, model}` settings pair over a v1 OpenAI-compatible custom provider; keys out-of-config; AI off by default; ranked last.**

1. **Keep the ghost path LLM-free; put AI behind the generators pattern.** The engine-side trait handles provider HTTP, auth, deadline (kill), and a stale-while-revalidate cache keyed to the typed segment; the pure model gains an `Ai` arm in `provider_candidate` that reads only the cache, exactly like `generator_candidate` reads `GeneratorSets`. Reuse `autosuggestions_delay_ms` as the natural debounce: the typed segment must be stable before a fetch fires, so keystrokes never queue network work and the sync contract is untouched. This is the only architecture every peer's evidence supports — the vendors that tried LLM ghost text (Q/Kiro) withdrew it, and the one that leads the category (Warp) keeps AI out of the typing path entirely.
2. **Settings surface: one pair, feature-scoped.** A single `autosuggestions_ai = { provider = "…", model = "…" }` selection (Zed's `LanguageModelSelection` minus the knobs DropTerm doesn't have), defaulting to disabled — the off state is the consent gate, per Warp's disable-AI toggle framing. If AI later backs more surfaces, grow sibling keys (`<feature>_model`) the Zed way rather than one global model key.
3. **v1 ships exactly one provider: `custom` OpenAI-compatible** (`api_url`, `model`, optional headers), because four of four peers implement generic-URL support and it covers OpenAI, Anthropic-via-gateway, OpenRouter, LiteLLM, Ollama, LM Studio, vLLM, and corporate gateways without per-vendor code. Named providers become additively registered trait impls later, Zed-style. Model listing (`GET /v1/models`) with capability probing mirrors Zed's `auto_discover` and feeds a future settings-UI picker; until then the model is a config string (Kiro's `chat.defaultModel` precedent).
4. **Keys: environment variable first (`DROPTERM_AI_API_KEY` style, Zed's derived-name convention), secret store second, never the config file** — the one rule every peer states positively and Copilot CLI documents the failure of.
5. **Merge rank: last, below Generator.** An AI candidate is the most stale and the most foreign truth in the system — it must never outrank history or local listing, the same reasoning that already pins Generator under the live providers (suggest.rs:494-502). Provenance is already carried by `Showing.source`, so the UI can label AI ghosts honestly.
6. **Exposure framing: request-scoped, minimal context.** What leaves the machine is the typed line plus whatever prefix context the request needs — the "prompts and context" framing Warp documents — behind the feature's own off-by-default toggle. Failure stays silent per the house contract: a failed or slow AI fetch degrades to `None`, never to a wrong suffix.

**Rejected alternatives:**

- **Inline streaming LLM ghost text on the keystroke path.** No peer ships it as a supported feature; the one that did removed it (Kiro CLI 3.0.0). It would break the pure-sync model (network on the guard chain) and the silence contract. Revisit only as an engine-cached prefetch — same shape as above, not a different one.
- **ACP as the extensibility answer.** ACP is editor↔agent chat over stdio/HTTP with sessions, prompts, and diffs — no completion surface. Adopting it would make DropTerm an agent host to get a feature ACP does not carry, and it violates the never-a-plugin-registry ruling already written into the seam (suggest.rs:41-42).
- **Named per-vendor providers at v1 (OpenAI adapter, Anthropic adapter, …).** Zed maintains ~20 provider modules for a feature set an order of magnitude larger than one suggestion source, and still needed the compatible maps. The trait keeps named providers cheap to add later; shipping them first is maintenance before use.
- **Keys in the config file.** Every peer that stores keys stores them out-of-config (keychain, secure storage, encrypted secret store); the one documented in-file store (Copilot `providers.json`) self-labels the plaintext hazard. DropTerm's config is serialized and test-pinned against docs — putting secrets there would also leak them into the docs gate.
- **A Warp-style "Auto" routing tier.** Auto requires a multi-provider backend with routing and fallback machinery (Warp's is hosted inference). With zero first-party providers at v1, there is nothing to route between; the pair key already lets the user change their mind.
