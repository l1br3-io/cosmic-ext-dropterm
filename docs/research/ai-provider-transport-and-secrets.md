# What does DropTerm's pinned build need to carry an AI capability end to end: HTTP transport with streaming, provider wire shapes, key storage on Linux and COSMIC, and a seam through which plugins can use the host's AI?

**Question:** What does DropTerm's pinned build need in order to carry an AI capability end to end — an HTTP transport with streaming, the provider wire shapes and the crates that speak them, a place to keep API keys on Linux and COSMIC, and a seam through which a plugin can use the host's AI — building on (not re-arguing) the ruled v1 shape in [ai-completion-providers](ai-completion-providers.md)?

**Date:** 2026-11-26

**TL;DR:** Everything hard is already in the pinned graph — `gpui-pre-http-client` (a streaming-capable `HttpClient` trait) is an unconditional dependency of `gpui-pre` itself, `gpui-pre-reqwest` (reqwest 0.12.15, the whole rustls stack) is already resolved in the lock and the graph-pin test anticipates it, the multi-thread tokio sidecar runtime is running for D-Bus, and — the record-changing find — `oo7` 0.6.0, a pure-Rust Secret Service/keyring client Zed itself uses, is **already compiled into every Linux build** as a hard dependency of `gpui-pre-linux`, sharing DropTerm's own zbus 5.19.0. What remains is small and additive: two direct dependency lines, a thin ~200-line `HttpClient` adapter (Zed's `reqwest_client` is the worked example), a hand-rolled OpenAI-compatible chat/SSE client over the ruled `{provider, model}` pair, key handling that extends the ruled env-first order with oo7 second and COSMIC's gnome-keyring-backed `org.freedesktop.secrets` as the store it finds, and a token-matched request→`HostEvent` AI facility that reuses the Lua host's existing query pattern. No hard blockers; three spikes before commitment.

## Findings

### 1. The transport trait is already in the build, ungated, and it streams

- `gpui-pre-http-client` 0.3.12 is the snapshot of Zed's `http_client` crate (manifest metadata: `zed-crate = "http_client"`, `zed-rev = d2a4fb6…`) — the `HttpClient` trait, request-extension surface, wrappers, and test fakes. It carries **no** HTTP implementation of its own (`gpui-pre-http-client-0.3.12/Cargo.toml` has no reqwest/hyper dependency at all).
- It is **not feature-gated**. `gpui-pre` 0.3.12 declares it as a plain (non-optional) dependency (`gpui-pre-0.3.12/Cargo.toml:359-361`), and there is no `http_client = […]` feature in gpui-pre's feature list (lines 53-92) — the only feature touchpoint is `test-support` enabling `http_client/test-support` (`:82`), which switches on the `FakeHttpClient` test fakes. The ruled feature set (`wayland` + `font-kit`) is irrelevant to it: the trait crate is in every gpui-pre build, and the lock confirms it (`Cargo.lock:2469` under gpui-pre, `:2652` under gpui-pre-linux). DropTerm's dev-dependency on gpui with `test-support` (`dropterm/Cargo.toml:224`) therefore already makes `FakeHttpClient` available in test builds.
- Streaming is native to the trait's shape: `HttpClient::send` returns `BoxFuture<anyhow::Result<Response<AsyncBody>>>` (`http_client.rs:123-126`), and `AsyncBody` implements `futures::AsyncRead` — the response variant is an `AsyncReader(Pin<Box<dyn AsyncRead + Send + Sync>>)` (`async_body.rs:14-41`, `poll_read` at `:114-131`) plus an `http_body::Body` adapter that emits 8 KiB frames (`:133-152`). Incremental response reads — exactly what Server-Sent Events need — are supported at the trait level. The request side carries `AsyncBody::from_reader` for streaming uploads, a `Json` newtype (`:93-103`), `RequestTimeout` (whole-request deadline including body, `http_client.rs:51-53`), `RedirectPolicy` (`:17-23`), and pre-validated `CustomHeaders` (`:66-86`) — the user-supplied-header surface Zed validates once at settings load.
- Consequence: DropTerm can adopt the trait by adding one direct dependency line (`gpui-pre-http-client = "=0.3.12"`, needed because a crate must be a direct dependency to be `use`-able) and naming an implementation — nothing new enters the graph.

### 2. gpui-pre-reqwest is reqwest 0.12.15, pinned in the family, waiting as the implementation

- `gpui-pre-reqwest` 0.12.15 **is reqwest itself** — manifest description "higher level HTTP client library zed-industries/request@c156624", repository seanmonstar/reqwest, license MIT OR Apache-2.0, lib renamed `gpui_pre_reqwest`. It is Zed's reqwest fork (`zed-industries/reqwest`) published under the snapshot family's namespace, riding "its own 0.12 line (its semver universe)" — language the graph-pin test already anticipates (`dropterm/src/main.rs:569-573`: "gpui-pre-reqwest rides its own 0.12 line … every other family crate is a 0.3.12 snapshot cut").
- It is in the lock (`Cargo.lock:2755-2803`) with the full stack resolved: hyper 1.12 / hyper-util 0.1.21 / http 1.5 / h2 0.4.20, rustls 0.23.46 + tokio-rustls 0.26.6 + hyper-rustls 0.27.10 + rustls-native-certs 0.8.5 (system CA store), `ring` 0.17.14, tokio-socks, tokio-util. One caveat on "present": the only crate that declares it, `gpui-kit-assets` 0.9.1, declares it under `[target.'cfg(target_family = "wasm")']` (`gpui-kit-assets-0.9.1/Cargo.toml:105-117`, features `charset, http2, macos-system-configuration, multipart, rustls-tls-native-roots, socks, stream`) — so it is lock-resolved and, per the build tree's fingerprints, **not compiled on Linux today** (settled; see Unverified). Adding it as a direct dependency compiles it for the first time; no new *crates* enter, only build time. Zed's own workspace pins the identical fork shape (`zed-reqwest 0.12.15-zed`, features `http2, macos-system-configuration, rustls-tls-native-roots, socks, stream`, `default-features = false` — zed main `Cargo.toml`, fetched 2026-11-26), which is the feature set to declare.
- SSE needs the `stream` feature: `Response::bytes_stream` is `#[cfg(feature = "stream")]` (`src/async_impl/response.rs:357-359`). Zed's adapter is the worked example of the whole seam — three lines of body plumbing:

  ```rust
  let bytes = response.bytes_stream()
      .map_err(futures::io::Error::other).into_async_read();
  let body = http_client::AsyncBody::from_reader(bytes);
  ```

  (`crates/reqwest_client/src/reqwest_client.rs` at zed main, fetched 2026-11-26; it also maps `RedirectPolicy`→redirect policies, `RequestTimeout`→per-request timeout with a test proving it fires mid-body, and proxy env handling with `no_proxy`.)
- Execution context: reqwest 0.12's async client contains no internal `tokio::spawn` for requests (grep over `src/async_impl/` found spawns only in the h3 client and the blocking wrapper), so the caller's executor drives the futures — and those futures need a tokio reactor for hyper/TLS/timers. DropTerm already runs one: the D-Bus sidecar thread builds a `new_multi_thread().enable_all()` runtime and blocks on it for the process lifetime (`dropterm/src/dbus.rs:92-107`). AI requests should be built and awaited there, with results marshaled to the UI or Lua host threads over `std::sync::mpsc` — the same discipline the Lua host already states ("no tokio channel crosses the bridge", `lua_host.rs:8-11`).

### 3. What one "OpenAI-compatible" client covers, and where the others diverge

- **The compatible family** (what the ruled v1 `custom` provider reaches):
  - **OpenAI Chat Completions**: `stream: true` yields SSE `data:` chunks of object `"chat.completion.chunk"` with `choices[].delta` (`role`, `content`, `tool_calls`), `choices[].finish_reason` (`"stop" | "length" | "tool_calls" | "content_filter"`), and a final usage chunk (the SDK chunk type carries a `usage` field gated on the `include_usage` stream option — openai-python `types/chat/chat_completion_chunk.py`, fetched 2026-11-26; OpenRouter's docs confirm the convention from the consumer side: its final usage chunk "follows OpenAI's spec", see below). Tools: request `tools: [{type: "function", function: {name, description, parameters}}]`; the assistant replies with `tool_calls: [{id, type: "function", function: {name, arguments}}]` where `arguments` is a **JSON-encoded string** the docs warn to "validate… before calling your function" (`types/chat/chat_completion_message_function_tool_call.py`); the follow-up is a `role: "tool"` message carrying `tool_call_id`. Streaming tool arguments arrive as fragments keyed by `delta.tool_calls[].index` (`chat_completion_chunk.py`, `ChoiceDeltaToolCallFunction`). Models: `GET /v1/models` returns `data[].{id, object: "model", created, owned_by}` (`types/model.py`; the API hub shows the `Authorization: Bearer` request, developers.openai.com/api/reference, fetched 2026-11-26).
  - **OpenAI Responses API** exists in parallel — the hub steers "direct model requests, tool use…" to it, and its streaming vocabulary is far larger (`response.output_text.delta`, `response.output_item.added`, `response.function_call_arguments.delta`, `response.completed`, `response.failed`, `response.incomplete`, MCP/image-gen/shell events — `types/responses/response_stream_event.py`). The OpenAI-compatible ecosystem below standardized on Chat Completions, not Responses; LM Studio is the one local server that also serves `/v1/responses` (its docs note "Codex is supported because LM Studio implements the OpenAI-compatible `POST /v1/responses` endpoint").
  - **Ollama** (`http://localhost:11434/v1`): compatibility is "experimental and subject to major adjustments including breaking changes"; the API key is "required but ignored". `/v1/chat/completions` supports streaming, JSON mode, vision, `tools` — but tool *streaming* is "coming soon" and `tool_choice` is unsupported; `/v1/completions`, `/v1/models` (with `created` = last-modified, `owned_by` defaulting to `"library"`), `/v1/models/{model}`, `/v1/embeddings` (`docs/openai.md` at main, fetched 2026-11-26). The **native** API diverges: `/api/chat` streams NDJSON objects (`message.content` deltas, terminal line with `done: true` + eval stats), carries `tools` with `role: "tool"` follow-ups keyed by `tool_name`; `GET /api/tags` lists local models (`models[].{name, size, digest, details.parameter_size, …}`), `POST /api/show` reports `capabilities` (`docs/api.md`, fetched 2026-11-26).
  - **llama.cpp `llama-server`**: serves `/v1/chat/completions`, `/v1/completions`, `/v1/models` ("the returned list always has one single element" — one model per server instance, `--alias` overridable), `/v1/embeddings`; "OpenAI-style function calling is supported with the `--jinja` flag"; grammar/`--json-schema` constrained outputs; native `/completion` is explicitly "not OAI-compatible"; SSE keep-alive pings via `--sse-ping-interval`; and the caveat is load-bearing: "While no strong claims of compatibility with OpenAI API spec is being made, in our experience it suffices to support many apps" (`tools/server/README.md` at master, fetched 2026-11-26).
  - **LM Studio** (port 1234): "Supported endpoints" table lists `GET /v1/models`, `POST /v1/responses`, `POST /v1/chat/completions`, `POST /v1/embeddings`, `POST /v1/completions`; a dedicated Tool Use page exists under OpenAI Compatibility; the native REST API v0 (`/api/v0/…`) adds loaded/unloaded state and TTFT stats (`lmstudio.ai/docs/app/api/endpoints/openai`, fetched 2026-11-26).
  - **OpenRouter** (`https://openrouter.ai/api/v1`): SSE `data:` chunks ending with `data: [DONE]`, keep-alive comment lines `": OPENROUTER PROCESSING"` — "If you parse the stream by hand, skip lines that start with `:` before calling `JSON.parse`" — mid-stream errors arrive as events while HTTP stays 200, and the final usage chunk "contains one choice with a content-free `delta` that repeats the `finish_reason`" (deviation from OpenAI's spec, which it otherwise follows) (`docs/api-reference/streaming`, fetched 2026-11-26). `GET /api/v1/models` is a public catalog (no auth required) returning `data[].{id (routable slug, e.g. `anthropic/claude-3.5-sonnet`), name, canonical_slug, pricing}` (`docs/api-reference/list-available-models`, fetched 2026-11-26).
  - Net: **one hand-rolled Chat Completions + SSE client covers OpenAI, Ollama, LM Studio, llama.cpp, OpenRouter, vLLM-class servers, and corporate gateways**; `GET /v1/models` reaches all of them (llama.cpp degenerately; OpenRouter auth-free). The deltas are field-tolerance details (OpenRouter's comment lines and usage chunk; Ollama's ignored key; llama.cpp's single model), all handled by a tolerant client, not by per-vendor code.
- **The named-vendor natives diverge structurally**, which is the ground the v1 ruling already stood on ("named per-vendor adapters rejected"):
  - **Anthropic Messages**: auth is `x-api-key` + `anthropic-version` headers (not Bearer); `stream: true` yields *named* SSE events `message_start` → `content_block_start`/`content_block_delta`/`content_block_stop` → `message_delta` → `message_stop`, with `ping` and in-stream `error` events; deltas are typed (`text_delta`, `input_json_delta` with `partial_json` accumulation, `thinking_delta`, `signature_delta`); tool use is a `tool_use` content block whose `input` fills from `partial_json` chunks and whose stream ends with `stop_reason: "tool_use"`; usage in `message_delta` is cumulative (`platform.claude.com/docs/en/api/messages-streaming`, fetched 2026-11-26). Nothing here matches the Chat Completions shape.
  - **Google Gemini**: native base is `POST /v1beta/models/{model}:generateContent` and `:streamGenerateContent`; tools are `functionDeclarations` (JSON Schema), responses carry `functionCall` parts and follow-ups `functionResponse` parts; the models list is `GET /v1beta/models` with a different resource shape (`name: "models/{id}"`, `supportedGenerationMethods`) (`aistudio.google.com/api-reference/generate-content`, `/api-reference/models`, fetched 2026-11-26). The docs also show a newer "interactions" endpoint with `?alt=sse` (`aistudio.google.com/docs/text-generation`, fetched 2026-11-26) — Google's reference surface is actively reorganizing (flagged under Unverified). Neither shape is reachable by a pure OpenAI-compatible client; Wave's `ai:apitype` enum (`openai-chat`, `openai-responses`, `google-gemini`) is the peer evidence that Gemini needs its own adapter (see [ai-completion-providers](ai-completion-providers.md) finding 4).

### 5. Secret storage: peers converge on the OS store; COSMIC ships one; oo7 is already in the binary

- **Peers:**
  - **Zed**: keys live in the system keychain with env-var override ("Keys saved through Zed are stored in the system keychain, not in `settings.json`"; provider id → `<PROVIDER>_API_KEY` — quoted in [ai-completion-providers](ai-completion-providers.md) finding 7). The Linux mechanism is now pinned from the workspace manifest: `oo7 = { git = "https://github.com/zed-industries/oo7", rev = "731c1215edb6905876c6137ab300428c7b8d7c13", version = "0.6", default-features = false }` in zed main's `Cargo.toml` — Zed forks oo7 0.6 and ships it.
  - **Wave**: "Instead of storing API keys directly in the configuration, you should use Wave's secret store to keep your credentials secure", set via `wsh secret set OPENAI_KEY=…`, and "Secrets are stored encrypted using your system's native keychain" — with provider presets auto-deriving secret names (`OPENAI_KEY`, `OPENROUTER_KEY`, `GOOGLE_AI_KEY`, …) surfaced in config through a key whose doc description is "Name of secret containing API token (auto-set by provider)" (`docs.waveterm.dev/waveai-modes`, fetched 2026-11-26). Same rule as Zed, OS-keychain backing.
  - **Warp**: "Personal API keys are stored in your device's secure storage." and "Warp does not retain your personal API key." — and even BYOK prompts "pass through Warp's servers to that provider" (`docs.warp.dev/agents/inference/bring-your-own-api-key`, fetched 2026-11-26). DropTerm has no server, so the honest analog is: keys stay on the machine, requests go provider-direct.
  - **VS Code**: `context.secrets` is "A global storage for secrets (or any information that is sensitive) that will be encrypted"; "For VS Code desktop, this leverages Electron's safeStorage API" (`code.visualstudio.com/api/extension-capabilities/common-capabilities`, fetched 2026-11-26). Electron's safeStorage on Linux picks among "kwallet, kwallet5, kwallet6 and gnome-libsecret" and — the cautionary ladder — "If no secret store is available, items stored using the safeStorage API will be unprotected as they are encrypted via hardcoded plaintext password. You can detect when this happens when safeStorage.getSelectedStorageBackend() returns `basic_text`" (`electronjs.org/docs/latest/api/safe-storage`, fetched 2026-11-26). Copilot CLI's `providers.json` plaintext credentials remain the counter-example that documents its own flaw ([ai-completion-providers](ai-completion-providers.md) finding 6).
- **The crates:**
  - **oo7** 0.7.3 upstream (MIT, MSRV 1.92, repo `linux-credentials/oo7`, 4.3M downloads, updated 2026-11-21): "James Bond went on a new mission and this time as a Secret Service provider" — zbus-based Secret Service client, XDG portal Secret integration via ashpd, and a **sandboxed local encrypted-file backend** (keyfile) for when no service runs. Runtime selectable: `tokio` (`zbus/tokio`) or `async-std` (`zbus/async-io`) features; crypto via `native_crypto` (aes/cbc/hkdf/pbkdf2/sha2) or openssl.
  - **The decisive fact: oo7 0.6.0 is already in DropTerm's lock.** `gpui-pre-linux` 0.3.12 — compiled into every DropTerm Linux build through `gpui_platform`'s `wayland` feature, which is "the consumer-side switch into the Linux crate's wayland backend" (`dropterm/Cargo.toml:36-38`) — declares `oo7 = "0.6"` non-optionally with `features = ["async-std", "native_crypto"]`, `default-features = false` (`gpui-pre-linux-0.3.12/Cargo.toml:160-166`), and the lock carries `oo7 0.6.0` with aes/ashpd/pbkdf2/zeroize/zbus/zvariant (`Cargo.lock:4886-4919`). Because the lock holds exactly one zbus entry (5.19.0, `Cargo.lock:8885`), oo7 resolves against **the same zbus DropTerm itself pins** — no duplication, no new crates; a `dropterm` dependency line on `oo7 = "0.6"` with the same features only names what is already compiled.
  - **keyring** 4.2.0 (MIT OR Apache-2.0, MSRV 1.88, now under the open-source-cooperative org, updated 2026-08-29): refactored into per-store crates; its `default`/`v1` feature picks `zbus-secret-service-keyring-store` as the Linux native store (docs.rs + crates.io features, fetched 2026-11-26). Whichever zbus major that store crate wants, it will not unify with 5.19 unless it is 5.x (Unverified) — so keyring likely *duplicates* the zbus graph that oo7 already fills.
  - **secret-service** 6.0.0 (MIT OR Apache-2.0, updated 2026-11-22): requires **zbus ^6** (dependencies endpoint) — a second major of the D-Bus stack. Duplicates; and unnecessary given oo7.
  - **dbus-secret-service** 4.2.0: mandatory dependency on the `dbus ^0.9` crate — the **libdbus C binding** (dependencies endpoint). Rejected on the project's pure-Rust D-Bus discipline (the graph holds no libdbus today — no `dbus`/`libdbus-sys` entry in the lock).
- **COSMIC ships a Secret Service provider — verified at the source.** COSMIC's session script starts it explicitly: `if [ -d "$XDG_RUNTIME_DIR/keyring" ]; then eval "$(gnome-keyring-daemon --start --components=pkcs11,secrets,ssh …)"` — the `secrets` component is gnome-keyring's `org.freedesktop.secrets` provider (`pop-os/cosmic-session`, `data/start-cosmic` at master, fetched 2026-11-26). It is not COSMIC-native code — the desktop borrows gnome-keyring — and community reports note first-login default-keychain quirks (cosmic-epoch issue #1635, 2025-02; Fedora discussion "GNOME Keyring on COSMIC", 2025-07, both fetched 2026-11-26, secondary corroboration). Pop!_OS inherits the same session script. So a Secret Service store is the *expected* case on the primary desktop; the design must still answer "no service running" (sway without a keyring daemon, for instance) — that is what oo7's keyfile backend and the ruled env-var-first order are for.
- **The fallback ladder** (extending the ruled "environment variable first, secret store second"): env var → Secret Service via oo7 (only when the user opts in by storing a key; never probed silently) → nothing automatic. A mode-0600 plaintext file is *not* proposed as an automatic fallback: Electron's `basic_text` (hardcoded-password "encryption") is exactly the failure mode peers can at least detect, and DropTerm should do better by refusing rather than degrading — an explicit user action with a stated warning would be the only path to a file, and even that is better served by oo7's encrypted keyfile backend (Unverified: the keyfile backend's exact threat story — where its master key lives — was not read this session).

### 6. The plugin-facing async seam: the precedents all converge on ask-host → answer-as-event

- **The physics:** a Lua script cannot make a network round-trip under DropTerm's bounds. The host's debug hook counts VM instructions with a 100 ms soft bound and a 1 s hard cap, and "a script blocked inside a C call (`io.read` on a pipe) … executes no main-thread VM instructions to trip the hook" — so a blocking HTTP call is both too slow to permit and structurally un-interruptible (`lua_host.rs:29-41`). A synchronous `dropterm.ai(prompt)` would either freeze the host thread for seconds or hang forever.
- **Precedents, all pointing the same direction:**
  - **Neovim `vim.system(cmd, opts?, on_exit?)`**: the async form takes an `on_exit` callback — "Called with the result on process exit and output pipes closed" — and returns a `SystemObj` (`wait`, `kill`, `write`, `close`); `wait()` blocks but pumps events (`vim.wait(…, 200, true)`); the callback form is the sanctioned non-blocking shape (`runtime/lua/vim/_core/system.lua` at master, fetched 2026-11-26). `plenary.nvim`'s curl shows the ecosystem's answer for HTTP specifically: `opts.callback`/`opts.stream` deliver parsed responses or stream chunks, while the default synchronous call "blocks the Neovim main loop until completion" (`lua/plenary/curl.lua` at master, fetched 2026-11-26) — the blocking default is the anti-pattern to avoid.
  - **WezTerm**: DropTerm's Lua host exists precisely to diverge from WezTerm's "GUI-thread Lua" (`lua_host.rs:6-11`); WezTerm's documented process APIs split the same way — `wezterm.run_child_process` returns output (synchronous), while `wezterm.background_child_process` is fire-and-forget: "it will attempt to spawn that command in the background. This function doesn't return any value." (`docs/config/lua/wezterm/background_child_process.md` at main, fetched 2026-11-26). WezTerm's HTTP API story could not be pinned this session (docs paths 404; see Unverified).
  - **kitty kittens**: the async surface is a *process boundary* — kittens are separate Python programs; remote control is capability-scoped by generated passwords ("This will use a secure generated password to restrict remote control") and "by default, for security, child processes launched by your kitten cannot use remote control" (`sw.kovidgoyal.net/kitty/kittens/custom.html`, fetched 2026-11-26). The lesson for DropTerm is capability-scoping, not mechanism (its scripts are in-process by the ruled tiering in [terminal-plugin-systems](terminal-plugin-systems.md)).
  - **VS Code `vscode.lm`**: the promise-based shape is the host-side template — `lm.selectChatModels({vendor, id, family})` returns an array (async), `model.sendRequest(prompt, options, token)` returns a streaming async-iterable consumed with `for await`, takes a `CancellationToken`, and carries a consent gate: "selectChatModels should be called as part of a user-initiated action, such as a command" (`code.visualstudio.com/api/extension-guides/language-model`, fetched 2026-11-26). The lifecycle record already gated "a progress slot … only when the host grows asynchronous work" ([vscode-extension-lifecycle-rea](vscode-extension-lifecycle-rea.md) incorporation item 5) — an AI facility is exactly that growth.
- **Design constraints a `dropterm.ai` seam must satisfy in DropTerm's host-thread model** (each from the pinned sources above):
  1. **Script calls are non-blocking asks; answers return as events.** The vocabulary pattern already exists: `QuerySegments`/`QueryTabTitles`/`PanelAsk` carry a `token`, "the reply lands as a [`HostEvent`] arm matched by token: stale until it arrives, and the … keeps its prior" (`lua_host.rs:105-142`). An AI ask joins as new arms — "The vocabulary stays closed: new commands join as new arms with the module that needs them, never by widening these semantics" (`lua_host.rs:108-109`).
  2. **The request executes off the host thread, on the tokio sidecar**, and the completion marshals back through the `LuaHostHandle` (`send`/`emit`, `lua_host.rs:394-413`, `:558-577`) — never a direct call into mlua from a foreign thread (the interpreter lives and dies on its one thread; "no tokio channel crosses the bridge", `lua_host.rs:8-11`).
  3. **Stale answers are discarded at the drain**, per the soft-bound contract — an AI answer arriving after its dispatch went stale is dropped, never replayed (`lua_host.rs:30-37`).
  4. **Hot reload kills in-flight callbacks by design**: a `Reload` recreates the interpreter whole, and answers arriving for the old generation must be dropped, not delivered (the reload semantics, `lua_host.rs:43-50`).
  5. **No streaming into Lua at v1**: SSE chunk-by-chunk delivery into script callbacks multiplies the stale/generation checks and gives scripts a long-lived session object the reload model cannot clean up; the host consumes streams internally (ghost text per [ai-completion-providers](ai-completion-providers.md)) and hands scripts whole results.
  6. **Consent and capability scoping**: the feature is off by default (the ruled consent gate), the ask carries only what the script passes plus the configured `{provider, model}` — never other tabs' content — and the answer is labeled as model output (untrusted) at the port.

### 7. Security checklist mapping (the named sections)

Against `.agents/references/security-checklist.md`:

- **AI / LLM Security** (`security-checklist.md:192-201`): model output is untrusted data — it must never reach a command line, file path, or eval path without host-side validation; the OpenAI SDK's own docs warn tool arguments are model-generated and to "Validate the arguments in your code before calling your function" (finding 3), and DropTerm's port should treat any `dropterm.ai` result the way OSC payloads are treated: parsed, bounded, never executed. Prompt injection is assumed — permissions live in code (the host decides what an AI-assisted verb may do), not in a system prompt; secrets and cross-tab content stay out of prompts (LLM02/LLM07, `:233-249`).
- **Data Protection** (`:134-143`): what leaves the machine is the typed prompt plus declared context, over HTTPS (rustls with the system CA store — corporate proxies work), only when the user-enabled feature is invoked; nothing is logged — the failure-stays-silent contract already in the suggest model ("a failed or slow AI fetch degrades to `None`") doubles as the no-secrets-in-logs rule; keys never enter the config store (whose RON files are watched, serialized, and docs-pinned — a secret there would leak into the docs gate) and are zeroized on drop (oo7 already pulls `zeroize`, `Cargo.lock:4917`).
- **Dependency Security** (`:145-190`): the recommendation adds exactly two crates, both **already in the lock at exact versions** (`gpui-pre-http-client 0.3.12`, `gpui-pre-reqwest 0.12.15` — checksums recorded, registry-provenanced, same publishers as the rest of the ruled family), plus optionally `oo7 = "0.6"` (same). No new transitive crates enter the graph; the graph-pin tests (`main.rs:552-592`) extend naturally (the family pin already special-cases gpui-pre-reqwest's 0.12 line). New crates *rejected* in finding 4 are rejected partly on this ground: every SDK candidate imports a second HTTP family whose provenance review burden duplicates the one already carried.

## What DropTerm has today

## Recommendation

**Proposed: finish the ruled AI capability with what the graph already carries — the `gpui-pre-http-client` trait over a thin `gpui-pre-reqwest` adapter on the existing tokio sidecar, a hand-rolled OpenAI-compatible Chat Completions + SSE client for the ruled v1 custom provider, keys via env-first with `oo7` (already in the binary) as the opt-in Secret Service store on COSMIC's gnome-keyring, and a `dropterm.ai` plugin facility built as new arms of the existing token-matched `HostCommand`/`HostEvent` vocabulary.**

1. **Transport: two dependency lines, one adapter module.** Declare `gpui-pre-http-client = "=0.3.12"` and `gpui-pre-reqwest = { version = "=0.12.15", default-features = false, features = ["charset", "http2", "macos-system-configuration", "multipart", "rustls-tls-native-roots", "socks", "stream"] }` (the exact feature set the lock already resolves and Zed ships), and write a ~200-250-line `HttpClient` impl modeled on Zed's `reqwest_client` (`bytes_stream → into_async_read → AsyncBody::from_reader`; redirect policy, request timeout, proxy env, `CustomHeaders` passthrough). Build the client and await its futures on the D-Bus sidecar's runtime (`dbus.rs:92-107`), never on the foreground executor.
2. **Wire: exactly the ruled v1 shape, hand-rolled.** One OpenAI-compatible client module: chat completions request/response serde types, SSE line parsing (`data:` / `:` comment tolerance per OpenRouter / `[DONE]` sentinel / incremental `tool_calls[].index` accumulation / `stream_options.include_usage`), and `GET /v1/models` listing. Named adapters (Anthropic Messages, Gemini, Responses) stay future additive impls of the same internal trait — the divergence evidence in finding 3 is the standing ground, not a to-do.
3. **Keys: extend the ruled ladder with what is already compiled.** Env var first (`<PROVIDER>_API_KEY` derived-name convention per Zed). Second, an opt-in store write path via `oo7 = "0.6"` (features `async-std`, `native_crypto` — the exact set gpui-pre-linux already builds) against `org.freedesktop.secrets`, which COSMIC's session provides through gnome-keyring's `secrets` component (finding 5). No automatic plaintext fallback: no service → the env var remains the answer, and the settings surface says so. Never a key in the RON config.
4. **Plugin seam: `dropterm.ai` as new arms of the closed vocabulary.** A `HostCommand` arm carrying `{token, request}` (prompt/messages, `{provider, model}`, caps), executed on the tokio sidecar, the answer landing as a token-matched `HostEvent` arm (or an `ai:*` event through the existing `Emit` path); stale-discard at the drain; generation-checked after reload; whole-result (no streaming into Lua); cancellable via a matching cancel arm; every constraint in finding 6 restated in the module doc.
5. **Model discovery rides `GET /v1/models`** per provider base URL (OpenAI, Ollama, LM Studio, llama.cpp's single entry, OpenRouter auth-free) — the settings picker's data source, mirroring Zed's `auto_discover` precedent; until a picker exists, the model stays the config string the ruling chose.
6. **Security posture per finding 7**: untrusted output, no secrets in prompts or logs, off-by-default consent, bounded consumption (one in-flight request per source, request + token caps, the generator deadline pattern), and the graph-pin tests extended so the two new direct deps stay pinned at their exact family lines.

**Rejected alternatives:**

- **A multi-provider SDK at v1 (`genai`, `async-openai`, `rig-core`, `llm`).** `genai` requires crates.io `reqwest ^0.13` and `async-openai`'s client is that same 0.13 line — each imports a second HTTP family beside the pinned `gpui-pre-reqwest` 0.12.15; `rig-core`'s MSRV 1.97.1 exceeds DropTerm's 1.93 outright; all four exceed the ruled scope (one custom provider, named adapters rejected).
- **Crates.io `reqwest` directly.** Same second-family duplication; gains nothing over `gpui-pre-reqwest`, which is the same code already pinned inside the ruled snapshot family and anticipated by the graph-pin test.
- **`ureq` (sync) or raw `hyper`.** ureq brings its own TLS stack and a blocking model needing a dedicated thread — a third HTTP design for a graph that already resolved the async one; raw hyper reimplements reqwest's conveniences (redirects, timeouts, proxy, TLS setup) for no pin benefit.
- **`dbus-secret-service` or `secret-service` for keys.** The former links libdbus (a C dependency the graph does not carry); the latter demands zbus ^6 — a second D-Bus major — when `oo7 0.6` already sits in the lock against the *same* zbus 5.19 and is the crate Zed itself ships.
- **Hand-rolling Secret Service D-Bus over zbus 5.19.** The protocol includes session negotiation and AES-CBC secret transport; oo7 already implements and ships it. Only worth a spike if the owner rules the oo7 dependency line unacceptable.
- **Streaming into Lua scripts at v1.** No interruptible-C-call escape exists, and per-chunk callbacks multiply the stale/generation checks the drain would have to enforce; the host consumes streams (finding 6, constraint 5).
- **A WezTerm-style GUI-thread synchronous HTTP call from scripts.** It contradicts the host-thread model that is lua-host's reason to exist (`lua_host.rs:6-11`), and the bounds make it un-shippable.
