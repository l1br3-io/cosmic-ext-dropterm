---
description: Implement tasks incrementally from module chunks — build, test, verify, commit. "auto" runs a whole module, "auto all" the whole initiative.
---

Load the `incremental-implementation` skill alongside `test-driven-development` with the `skill` tool.

## Artifact layout (see AGENTS.md "Spec & task artifacts")

- `SPEC.md` — master index: capability map, dependency direction, build order, per-module status.
- `SPEC-<module-id>.md` — a module's approved spec.
- `tasks/<module-id>.md` — the module's task chunk: the unit `/build` consumes.
- `tasks/plan.md` / `tasks/todo.md` — global aggregates generated by `/plan`.

## Modes

- `/build` — implement the *next pending task* of the next pending module (build order from `SPEC.md`), then stop.
- `/build <module-id>` — implement the *next pending task* of that module, then stop.
- `/build auto` — one approval, then *every task* of the next pending module.
- `/build auto <module-id>` — one approval, then *every task* of that module.
- `/build auto all` — one approval, then *every task of every pending module* in build order.

`$ARGUMENTS` selects the mode: `auto` alone = next pending module, `auto <module-id>` = that module, `auto all` = everything; anything else (or empty) is the single-task mode. Autonomous modes are not faster *per task* — same test-driven loop — they only remove human stepping *between* tasks.

## Default: one task

1. Pick the next pending task: read `SPEC.md` status, then the module's `tasks/<id>.md` chunk.
2. Load the chunk's context: its `SPEC-<id>.md`, the files it lists, existing patterns.
3. Write a failing test for the expected behavior (RED).
4. Implement the minimum code to pass the test (GREEN).
5. Run the full test suite to check for regressions.
6. Run the build to verify compilation.
7. Commit with a descriptive message.
8. Mark the task complete in the chunk, in `tasks/todo.md`, and in `SPEC.md`'s status table; stop.

## Autonomous: one module (`/build auto`)

Use this once a module's spec is approved and its chunk written, to collapse plan + build for that module into one run. Every task still earns a passing test and its own commit.

1. **Require an approved spec and a chunk.** The module must be marked approved in `SPEC.md` and have `SPEC-<module-id>.md` + `tasks/<module-id>.md`. Otherwise stop and point at `/spec` / `/plan` — do not invent requirements.
2. **Enforce build order.** If the module has pending dependencies, stop and name them.
3. **Establish a clean baseline.** Run `git status --porcelain`. If there are uncommitted changes outside the expected working artifacts (`SPEC*.md`, `tasks/`), stop and ask the user to commit, stash, or confirm. Autonomous per-task commits must not absorb unrelated local work.
4. **Single checkpoint.** Present the module's chunk (its task list) and wait for an unambiguous affirmative (e.g. "approve", "go", "yes"). Hedged responses are **not** approval. This is the only human gate for the module — after approval, run autonomously.
5. **Execute every task in the chunk** in listed order, running the full default loop (RED → GREEN → regression → build → commit → mark complete). Stage only the files that task touched plus its status updates — never `git add -A` blindly — one commit per task so any point is a clean rollback.
6. **Stop and ask the user** (do not push through) when:
   - a test can't be made to pass or the build breaks without an obvious fix → follow `debugging-and-error-recovery`
   - the spec is ambiguous, or a task needs a decision the spec doesn't cover
   - a task is high-risk or irreversible — anything touching secrets, destructive operations, or that you can't undo with `git revert` → follow `doubt-driven-development` and get explicit sign-off

   After the user resolves a blocker, they re-invoke `/build auto` — it resumes from the next pending task.
7. **Summarize at the end:** tasks completed, tests added, commits made, anything skipped, flagged, or left for the user.

## Autonomous: the whole initiative (`/build auto all`)

Same as `/build auto`, but the single approval covers **every pending module**, executed in `SPEC.md` build order, one commit per task. Use only when all pending module specs are already approved and you want zero checkpoints between modules. The same per-module context loading, clean-baseline check, and stop-and-ask conditions apply; the single checkpoint presents every pending module's chunk at once.

If any step fails, follow the `debugging-and-error-recovery` skill.
